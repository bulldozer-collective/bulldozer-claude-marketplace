# Sanity-Check with Bulldozer OS, When the Project Has One

If the project has a Bulldozer OS profile, two analyses ground the top-down pass in something observed rather than a purchased report — check for a completed run before falling back to a market research report:

- **`bdzGetProjectOfferStructure`** gives a market-concentration verdict (monopoly / oligopole / concentré / fragmenté / atomisé), a top-3 players' combined share **as a range, never a single figure**, and a list of tracked competitors each with an estimated revenue and headcount. Treat those competitor CA/effectif numbers as the tool's own directional estimates from partial public sources (Crunchbase, LinkedIn, Societe.fr) — cite them as such, never as verified figures in front of a client.
- **`bdzGetProjectDemandIntensity`** gives real search-demand grounding: query tiers (T1 direct-intent / T2 comparative / T3 informational), an estimated monthly volume per tier **as a range**, a capture score, and a verdict. It documents its own error margin explicitly (typically around ±50% per query) — use it to sanity-check whether the SAM you've built bottom-up is remotely plausible given actual search volume, not as a substitute for Keyword Planner or Semrush data.

Both require prerequisites (a completed value proposition analysis, a company with a website linked to the project) and run as an async job — if the state isn't `SUCCESS`, fall back to the manual top-down process above rather than stalling on it. Both calls also take a `targetProjectId` alongside the usual `customerId`/`projectId` — pass the project's own id again there, or the call is rejected before it ever reaches the state check. And once you have a result, judge how current it is by `startedAt`, never `createdAt`: the same analysis row is reused across relaunches, so `createdAt` can still show a months-old date right after a fresh run — `startedAt` is what actually moves.

**Before quoting a verdict, share, score, or note from either analysis, check whether it's been overridden.** Both tools return their narrative fields (offer-structure's `verdict.justification`, `verdict.top3Share`, `note`; demand-intensity's `captureScore`, `verdict`, `estimatedCapturableVolume`, `note`) as `{value, override, overridden}` rather than plain values — `value` is what the AI produced, `override` is a correction a client may already have made by hand. If `overridden` is true, cite `override`, not `value`; a sizing that repeats the pre-correction number is quoting something the client already fixed.
