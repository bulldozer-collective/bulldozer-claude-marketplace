# Standing Report Template and Data Sources

### Monthly template

```
## Attribution — [Month]
Model: [first-touch / last-touch / dual] · Data quality: [X]% of leads with source populated

### Channel contribution
| Channel | Spend | MQLs | SQLs | Pipeline | Closed-won | CAC | Payback |
|---------|-------|------|------|----------|-----------|-----|---------|

### What moved
- [Channel] — [what changed vs. last month, and the one number that shows it]

### Decision requested
- [Scale / hold / cut], on [channel], for [amount] — because [the number above]

### What this model cannot tell you
- [The blind spot of the chosen model, restated every month]
```

### Where the numbers come from

The report is only standing if the inputs are pulled, not typed. In Bulldozer OS:

- **Paid spend and delivery** — `bdzGetAdAnalytics` for the ad accounts already imported, per layer (`bdzGetAdLayer3` for creative-level detail). Google Ads spend comes through `bdzGetGoogleAdwordAccountRefreshConfig` accounts once imported. Always pass `from`/`to` explicitly: the tool defaults to a trailing 180-day window when they're omitted, so a call meant to pull "this month's" spend for the template above quietly returns a six-month average instead, with no warning that the window wasn't what was asked for.
- **Site and content behaviour** — `bdzRunGoogleAnalyticsReportTemplate` against a saved template, and `bdzCreateGoogleAnalyticsReportSchedule` with `frequency: MONTHLY` (the schedule tool also supports `DAILY` and `WEEKLY`) so the pull happens on its own each month rather than when someone remembers. Building that saved template dimension-by-dimension isn't the only path: `bdzApplyGoogleAnalyticsTemplatePreset` with `presetId: channel_attribution` creates one pre-filled for exactly this use case in a single call — confirmed live in the tool's own schema, alongside four other presets (`seo_performance`, `paid_traffic`, `conversion_funnel`, `audience_insights`) via `bdzListGoogleAnalyticsTemplatePresets`. It's a shortcut into the same `bdzCreateGoogleAnalyticsReportTemplate` path, not a different report type; what dimensions and metrics it actually pre-fills hasn't been checked against a real project. Every run of `bdzRunGoogleAnalyticsReportTemplate` also computes and stores anomaly detection for free, confirmed unchanged in the tool's own schema: any metric that deviates by more than 2 standard deviations from its history gets flagged. Don't recompute "what moved" by eyeballing two periods — `bdzListGoogleAnalyticsReports` returns a lightweight `hasAnomaly` boolean per stored report (cheap to scan across months), and `bdzGetGoogleAnalyticsReport` on a specific report ID returns the full `anomalyDetails`.
- **Pipeline and revenue** — the HubSpot connector. `get_campaign_attribution_reports` computes the model picked in Attribution Model Selection natively — pass `attributionModel` and group by `UTM_SOURCE`, `UTM_MEDIUM`, `UTM_CAMPAIGN`, `ASSET_TYPE` or `DEAL`, with metrics `REVENUE`, `DEAL_COUNT`, `DEAL_AMOUNT`, `CONTACT_COUNT` or `ATTRIBUTION_COUNT` — but every number it returns is scoped to closed-won deals only, and the whole call can fail on the missing `marketing.campaigns.read` scope before it ever gets that far (see the caution in Attribution Model Selection) — worded as a raw HubSpot API scope error in earlier checks, or, as of October 2026, as a connector message naming the scope and a reconnect-then-admin-if-locked fix. Confirm this call actually returns data on the client's portal before the first monthly report goes out — a missing-scope failure and an empty attribution period look the same on the page. Two mechanical requirements the tool enforces on top of that, confirmed by reading its live schema: the first call must either read the tool's own usage guidance first or accept the forced round-trip — submit without `hasReadToolInstructions` and it comes back `READ_TOOL_INSTRUCTION_REQUIRED` with the real instructions attached, then retry with `hasReadToolInstructions: true`; and a query heavy enough to run long comes back `PROCESSING` with a `taskId` to poll rather than the report itself. Neither is the scope error above — build for both before wiring this into an unattended monthly pull. For pipeline that's still open (the "Attributed pipeline" row above), pull DEAL records at any stage with `query_crm_data` or `search_crm_objects` instead.

Six cautions. First, each source counts a conversion by its own rules — GA4 counts sessions, the CRM counts deals, the ad platform counts platform-attributed conversions. Never add them; pick the CRM as the single source of truth for revenue and use the others for upstream volume only. Second, check that the ad accounts and the GA property are actually connected on the project before promising a monthly pull — an unconnected account returns nothing, not an error. Third, a single `startDate`/`endDate` window on `get_campaign_attribution_reports` does not filter the same field for every metric: `REVENUE` and `DEAL_AMOUNT` filter by deal close date, `DEAL_COUNT` filters by deal create date, `CONTACT_COUNT` and `ATTRIBUTION_COUNT` filter by touchpoint date. Pull revenue and deal-count for "this month" with the same date range and you're comparing deals that closed this month against deals that were merely opened this month — two different populations wearing the same column header. State which date each number in the monthly template is anchored to, or don't put them in the same row.

Fourth — and this is the one most likely to silently break the "Attributed pipeline" row above — object-level read access does not predict whether `query_crm_data` will actually run against that object. Confirmed directly on this connector: DEAL reads as fully available in schema discovery, and a `query_crm_data` SELECT against DEAL still failed outright, with a distinct OAuth scope error (`crm.hubsql.execute`, `reporting.full.read`, and `marketing.campaigns.revenue.*.read` all reported missing) — a different failure mode from the token-expiry and permission-modification errors this connector is already known to throw elsewhere. As of October 2026 that failure itself names a two-step fix rather than just the missing scopes: reconnect the HubSpot app to the agent and explicitly check those permissions during reconnection (none are granted by default, and this step needs no admin), and escalate to the HubSpot admin only if a permission shows a lock icon — meaning an admin has already disabled it for this app, so reconnecting again changes nothing. Don't default straight to "ask the admin"; it skips a self-service step that may be all that's needed. `search_crm_objects` is worth trying as a fallback on the same DEAL data in the meantime: it has been observed working in a session where `query_crm_data` failed on the same object, though nothing guarantees the two tools stay in sync going forward.

Fifth, a sudden jump in a channel's attributed GA4 credit month-over-month isn't always the silent under-threshold fallback described in What No Model Tells You above. GA4 went through an April 2026 recalibration of Data-Driven Attribution — converging secondary sources (no single official Google page opened directly this pass) report that it reset some properties back onto the data-driven model even where a different model had been manually selected, and rebalanced credit between channels in the process. Before writing "channel X's attributed revenue moved" into the What Moved section, check the portal's Attribution Settings for whether the model itself changed or reset that month — not only whether volume dropped below the DDA threshold.

Sixth, before doing either of the above by hand, check whether the OS already flagged it. Read `hasAnomaly` on the relevant `bdzListGoogleAnalyticsReports` summaries first — it's the cheapest possible first pass across several months of stored reports — and only pull `anomalyDetails` from `bdzGetGoogleAnalyticsReport` for the ones that come back flagged.

Seventh, `CONTACT_COUNT` on `get_campaign_attribution_reports` is not a new-contact or reach metric — its own live schema defines it as contacts whose interactions influenced a closed-won deal, scoped to the same closed-won pipeline as every other number this tool returns. Reading it as MQL volume or campaign reach overstates what it measures. For sessions, new contacts, and influenced contacts at the campaign level, `read_campaign_data` (operation `GET_ANALYTICS`) is the tool built for that; its `GET_CONTACTS` operation returns the actual contact IDs behind `NEW_CONTACTS_FIRST_TOUCH`, `NEW_CONTACTS_LAST_TOUCH`, or `INFLUENCED_CONTACTS` — each scoped to one campaign at a time, not a portfolio-wide pull.
