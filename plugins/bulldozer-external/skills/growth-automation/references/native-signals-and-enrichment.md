# Native Bulldozer OS Signals and Enrichment — Mechanics, Arbitrage and Lifecycle

## Step 1: Signal Detection Automation — native signal mechanics

**Native signal mechanics (`bdzCreateSignal`):** every signal is scoped to a project (`customerId`+`projectId`), requires a `type` from `bdzListSignalTypes` and a `config` object whose accepted keys depend on that type — an unrecognized key or an out-of-range value returns a 400 naming it, so read the type's config schema before configuring it. `leadListId` is mandatory and immutable once set: create the lead list first (`bdzCreateLeadList`) so every lead the signal produces lands there, owning the resulting contact and company. Cost is metered per lead at the type's `creditsPerLead`, frozen at creation and converted to jetons (0.5 credit = 7 jetons, up to 12 credits = 164 jetons) — when the jeton stack runs out the signal deactivates itself automatically and emails its creator, so this is a running cost to budget for, not a one-off setup fee. Don't conflate two separate persona mechanisms: `bdzCreateSignal` takes a top-level `personas` array, independent of any persona keys a given type's own `config` may accept (e.g. `targetPersonas`/`deliverPersonas` on some types). Only the config-level keys are documented as validated against the `SignalPersona` enum (listed by `bdzListSignalPersonas`, unrecognized value → 400) — the top-level `personas` field's own schema doesn't state that it draws from the same list, so don't assume it accepts the exact same values without checking against a real signal of the type in question. Check both fields regardless of that gap: setting only one where a type expects both leaves the signal under-targeted.

**Two create-time failures worth naming explicitly, confirmed by a direct re-read of `bdzCreateSignal`'s and `bdzListSignalPersonas`'s schemas, plus a real call to the latter, on 2026-10-12.** `bdzCreateSignal` returns 409 when a signal with the same `name` already exists in the project — names are unique per project (max 255 chars), so check `bdzListSignals` (filterable by `type`) for an existing signal before creating one, rather than re-running a failed build step blind and hitting the same conflict a second time. And `bdzListSignalPersonas` returns each persona as a pair — a `value` (the enum string the API actually accepts, e.g. `SIGNAL_PERSONA_HR_DIRECTOR`) and a human-readable `label` (e.g. `HR Director`) — only the `value` goes into `targetPersonas`/`deliverPersonas`; passing the `label` instead returns 400 naming it as an unrecognized persona, an easy trap when copying straight from the readable list.

**Check the plan tier and traffic geography of any external identification tool before scoping it, not just whether Bulldozer OS has a native equivalent.** The "no native equivalent" verdict on a row in the table above only means build it externally — it says nothing about which external tool, at which plan, will actually work for this client. RB2B (cited below for website-visitor identification) is a documented case: since a January 2026 repricing (dated 22 January 2026 by several independent sources), its free plan resolves company-level identity only, capped around 150 resolutions/month (raised from 100 at that same repricing — convergent across several independent GTM-tool comparison sites, never confirmed first-hand on RB2B's own site, which this environment cannot reach) — person-level data (name, email, LinkedIn URL) requires a paid plan — and person-level resolution itself is limited to US traffic; a visitor from Europe or Asia resolves at the company level on any plan. A client whose ICP traffic is majority non-US, or who expects to pilot on the free tier, will not get the "contact + Slack alert" workflow this skill assumes for that row (Step 3) — confirm the vendor's current plan and coverage with the client before committing to that shape of automation, rather than assuming the tool's original free-tier capability still holds.

**Arbitrage: when native stops being the default.** A native signal's `config` is a closed list — only the parameters and value ranges `bdzListSignalTypes` reports for that type are accepted, so it goes exactly as far as that list and no further. The moment a client's targeting needs a criterion the type's config doesn't expose (combining a job-posting match with a specific tech stack, or excluding a named list of existing customers before a lead ever lands), the native signal can't be shaped to fit — build it on Clay/Phantombuster instead, where the filtering logic is whatever you write. Cost is the other lever: the native signal's price is metered per lead regardless of volume and paid in jetons, while an external tool like Crunchbase or a Sales Nav seat is usually a flat subscription the client may already be paying for. At low-to-moderate lead volume the native signal still wins on setup time (no webhook, no separate contract) even when its per-lead credit cost looks higher on paper; past whatever volume makes the metered jeton spend exceed what the client's existing external subscription already costs for the same leads, the arbitrage flips — recompute it per client rather than assuming the native signal is always cheaper just because it's inside the platform.

**Lifecycle discipline for native signals.** `bdzCreateSignal` also takes an optional `dailyLeadLimit` (1–1000): set one on every new native signal, especially during the Phase 2 validation window (see Build Phases) — it caps exposure without anyone having to watch the signal by hand. `bdzUpdateSignal` changes `name`, `dailyLeadLimit`, `status`, or (only once, if none is set yet) `leadListId` on a live signal, and pausing (`status: SIGNAL_STATUS_INACTIVE`) costs nothing at the provider — never reach for `bdzDeleteSignal` to pause a signal or to change one of these fields: deleting removes the remote provider signal permanently, and rebuilding it means re-entering the whole config and losing the lead-list linkage history for what should have been a one-field change. A signal can also stop itself silently for two distinct reasons — the jeton stack running out, or a lead-list failure — both surface only as an email to the signal's creator and a flip to `SIGNAL_STATUS_INACTIVE`; resuming is a `bdzUpdateSignal` call back to `SIGNAL_STATUS_ACTIVE`, not a rebuild. Don't rely on that email alone: fold a periodic `bdzListSignals` check for `status = SIGNAL_STATUS_INACTIVE` into the monitoring layer (Step 5 / Phase 3) so a stopped signal is caught on the next hygiene pass rather than whenever someone happens to notice the pipeline went quiet.

## Step 2: Enrichment Automation — native alternative

**Native alternative for contacts Bulldozer OS already knows:** `bdzEnrichContact` refreshes an *existing* contact record from its LinkedIn URL (the URL is required — no URL on file means no enrichment) — it adds employment history automatically, and appends email/phone only when asked explicitly (+2 jetons each), overwriting the stored value even if the lookup finds nothing better. It is not a discovery tool and does not run a waterfall across providers, so it does not replace Clay for a brand-new signal lead that has no contact record yet — use it to refresh a contact already sitting in Bulldozer OS (e.g., one produced by a native signal above) rather than to enrich cold data from just a name and domain. It also requires the `SUBSCRIPTION_CAPABILITY_BASICS` subscription capability on the client's account — confirm the plan before proposing this path, rather than finding out from a failed call mid-build.

## Step 5: CRM Hygiene Loop — native option for the stale contact loop

- **Check the native option before wiring a Clay re-enrichment webhook for this loop.** If the stale contacts sit in a Bulldozer OS lead list, `bdzEnrichLeadList` re-enriches the whole list in one asynchronous call (poll `bdzGetLeadListEnrichment` — states are only `ENRICHING`/`DONE`, so read `errorCount` against `targetedCount` rather than expecting a failure state) — it already skips (free) any contact re-enriched less than 7 days ago, so a quarterly cadence never re-pays for a contact refreshed by an earlier signal or hygiene pass. Reach for Clay only when the stale contacts are scattered outside a lead list, or the loop needs an enrichment field `bdzEnrichLeadList` doesn't cover (it refreshes job history plus, on request, email/phone — nothing beyond that).
