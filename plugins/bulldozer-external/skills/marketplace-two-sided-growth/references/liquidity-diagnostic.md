# Liquidity Diagnostic — Detail

## Refusing the marketplace framing when a single-sided tool works

**Before running this diagnostic, refuse the marketplace framing if a single-sided tool solves the same problem.** The two-sided sequencing below is expensive to run — it asks a founder to build and fund both sides before either one works. The senior move is to ask, once, before Step 2: could one side get real value from a tool that doesn't require the other side to show up yet? A directory the buyer can search without a live supplier, a scheduling or invoicing tool a supplier would pay for on its own, a matching engine a buyer would use even with thin supply because it also does something useful stand-alone. This is the "come for the tool, stay for the network" pattern: ship the single-player utility first, earn the right to add the second side once the first side is retained on its own. It doesn't apply everywhere — some categories only have value once both sides are present (a true real-time match has no single-player version) — but skipping this question is how founders end up running the full cold-start sequence below for a problem a simpler product would have solved. If the answer is genuinely no, proceed.

## Calibrating the thresholds

**Treat these as starting points to calibrate, not fixed targets.** No audited, dated
study publishes a universal liquidity or supply-density threshold — the right number
moves with category, ticket size, and how often a buyer naturally repeats. Set them once
against the first weeks of real data for this marketplace (Step 7), then hold the
calibrated version, the same way a retention or conversion benchmark doesn't transport
from one business model to another.
