# Account Score Upload

**LinkedIn: Matched Audience + Tiered Campaigns**
LinkedIn Campaign Manager has no per-audience bid dial at all — no setting on a single campaign says "bid 50% higher for this segment" (Google Ads gives you exactly that at the ad group level for Search — see below). The native way to weight spend by tier on LinkedIn is one campaign per tier, each with its own bid and daily budget, plus exclusions between them so the same impression isn't bid on twice:
- Export Tier A accounts (ICP score ≥ 80) as a company list → upload as a Matched Audience → run in its own campaign with the highest bid cap and budget priority
- Export Tier B accounts (score 50–79) → upload separately → its own campaign, lower bid cap
- Export Tier C accounts (score <50) → add as an exclusion audience on both campaigns above, so Tier C accounts never absorb Tier A/B budget

**Google: Native Audience Bid Modifiers at the Ad Group Level (try this first — no volume floor, no Smart Bidding required)**
Where LinkedIn has nothing, Google Ads Search gives you two separate ways to weight bids by ICP tier. Start with this one: unlike the conversion-value mechanism below, it works from day one, runs under a manual bid strategy, and doesn't wait on enough monthly conversions to feed Smart Bidding.

- **Find the audience.** `bdzListSeaAudiences` lists what already exists on the account — Customer Match lists (`SEA_AUDIENCE_SOURCE_USER_LIST`, the ICP-tier seeds from Step 2) and Google's own combined audiences (`SEA_AUDIENCE_SOURCE_AUDIENCE`). Check `eligibleForSearch` before picking one for a Search ad group: a list Google doesn't consider Search-eligible is rejected outright, and the flag comes back `null` (not `false`) for the `AUDIENCE` source, which carries no such flag at all.
- **Attach it.** `bdzCreateSeaAdGroupAudience` attaches an audience to an ad group (L2) with a `bidModifier` (1.3 for +30%, 0.7 for −30%) — pass the audience's `id` and `source` together, exactly as `bdzListSeaAudiences` returned them; the two kinds route through different Google fields, and an id from one paired with the other's source fails. Leave `bidModifier` off and the audience only measures traffic, it doesn't bid.
- **The tool forces Observation mode — this is the safety net, not a detail.** The raw Google Ads API defaults a new audience criterion to Targeting (restricts delivery to that audience), the opposite of what the Google Ads UI defaults to on a Search campaign; attaching one straight through the API would silently cut the ad group's reach down to whichever tier was attached first. Bulldozer's tool always sets Observation instead, so tiering bids here never turns into an accidental targeting restriction. `bdzListSeaAdGroupAudiences`'s `observation` field is shared by every audience on that ad group, not set per audience — check it first if an ad group's impressions collapse right after adding a tier.
- **Retuning.** `bdzUpdateSeaAdGroupAudience` changes only the `bidModifier` — the audience a criterion points at is immutable, so swapping which list is attached means detaching and reattaching, never an update in place.
- **Don't confuse this with `bdzCreateSeaBidModifier`**, a separate tool that only ever adjusts by device (mobile/tablet/desktop). Audience and device bid modifiers live on the same ad group but never go through each other's tool.

This doesn't remove the need for exclusions discipline — Tier A and Tier C still shouldn't bid on the same impression — it just does the weighting inside one ad group's structure instead of three separate campaigns.

**Google: Offline Conversion Values (goes further, once volume allows)**
Instead of reporting all conversions at the same value (the default), upload tiered offline conversion values based on ICP score:
- ICP Tier A lead: conversion value = €500
- ICP Tier B lead: conversion value = €200
- ICP Tier C lead: conversion value = €50

Google's Smart Bidding then optimizes for high-value conversions, not conversion volume. The mechanism is sound and the direction is real; the "30–50% lower cost per ICP-qualified lead" figure circulating for this tactic traces to a single agency's own blog content rather than an audited study, so present it to the client as a plausible range worth testing for, not a guaranteed result.

**Setup, if the account runs through Bulldozer OS:** don't ask the client to do this upload by hand — `bdzCreateSeaConversionAction` (with `type=UPLOAD_CLICKS`; the default `WEBPAGE` type is refused for this and returns 400) creates the conversion action, then `bdzUploadSeaConversions` sends the CRM's qualified leads — ICP-tier value as `conversionValue`, tied back to the click by `gclid`/`gbraid`/`wbraid` — up to 2,000 rows per call. Two checks the tool itself flags as prerequisites, not optional: confirm `bdzGetSeaAutoTagging` is on first (no gclid on the clicks, nothing to upload), and read the `results` field of the upload response rather than trusting the HTTP status — Google runs this in partial-failure mode, so a 200 is returned even when every single row inside it was rejected.

**One constraint outside Bulldozer's control:** this upload uses Google's older "offline click conversion" mechanism, and Google closed it to new adopters on June 15, 2026 — an account that hadn't already called it between December 2025 and May 2026 gets rejected outright on the first attempt (`CUSTOMER_NOT_ALLOWLISTED_FOR_THIS_FEATURE`), whatever Bulldozer or you do right. Google's own recommended replacement going forward is the Data Manager API, and native HubSpot/Salesforce revenue-sync integrations are reported to be migrating to it under the hood — so a client already live on one of those native integrations should keep working. Check the account's history with this specific path (or its migration status, for a native CRM integration) before promising this mechanism to a client who has never run offline conversion uploads to this Google Ads account before.

**Without Bulldozer OS on the account** (or as a fallback): CRM → sync qualified leads with ICP score → offline conversion upload via a custom Google Ads API integration or the Salesforce/HubSpot native integration → Smart Bidding switches to value-based bidding (Target ROAS or Maximize Conversion Value, whichever label your account currently shows) instead of a flat cost-per-lead target. The same June 2026 cutoff applies to a custom-built integration calling the Google Ads API directly.

**Before you flip the switch:**
- The value tiers only teach the algorithm anything if each tier clears a minimum volume — and that threshold applies **per campaign, per tier**, not to the account's total conversion count. A rule of thumb: value-based bidding needs on the order of 30–50 conversions per month per campaign before it has enough signal to optimize on. An account converting 40 leads a month sounds like enough — split three ways across Tier A/B/C campaigns, none of them clears the floor, and every tier stays in a semi-permanent learning state while looking, on a monthly total, like it should be fine. Check the volume tier by tier before launching, not after a month of flat results. If Tier A volume is too thin on its own, start with two tiers (qualified / not qualified) instead of three — collapsing tiers is the right move, running an underfed tier "to see what happens" is not. If no tier clears the floor at all, don't force this mechanism prematurely — the native audience bid modifier above has no minimum volume requirement, since it's a static multiplier the account manages, not a signal Smart Bidding has to learn.
- Do not let a campaign already mid-learning-phase absorb this change and a budget or audience change in the same week — pick one lever, wait out the learning phase, then move to the next.

**Data checkpoint before this goes live:** this document uses "cost per SQL" and "cost per ICP-qualified lead" as the same thing — a lead that both matches the ICP criteria and has been marked qualified by whatever workflow the client already runs (an SDR call, a lead-scoring rule, an SQL handoff in the CRM). Confirm that's actually true for the account you're working on before quoting any threshold above: if "qualified" means something looser locally (an MQL, a form fill that hit a score cutoff with no human review), the 30–50 conversions/month rule of thumb and the tier definitions still apply, but to a noisier signal than the name suggests — say so to the client rather than letting the label do the work. The ICP score itself is only as trustworthy as the field it comes from. Confirm with whoever owns the CRM that the score is a single number, computed the same way for every lead, and check what share of qualified leads actually carry a score — a tiering system built on a field that's 40% empty will send the algorithm noise dressed up as signal. Revenue value should come from the CRM's own closed-won amount, never estimated from a match with ad-platform-reported conversions: the two will disagree, and averaging them creates a number that means nothing. The same discipline applies once the tiers are live and someone asks whether they're working: cost comes from the ad platform, the ICP-qualified lead count comes from the CRM — never the platform's own conversion count, which measures form fills, not the score you're bidding on. Divide one by the other and you get a real cost-per-ICP-lead; blend the two sources and the number won't reconcile with either system when someone checks it later.
