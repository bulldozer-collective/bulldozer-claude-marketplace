# Stakeholder Messaging Map

**Standard buying committee roles:**

| Stakeholder | Primary concern | What they're afraid of | Key message | Proof format |
|-------------|----------------|----------------------|-------------|-------------|
| **Economic buyer** (CEO, CFO, VP) | ROI, vendor stability, strategic fit | Wasting budget on something that doesn't scale | Revenue or cost impact + how we've done it for similar companies | Named customer results + analyst/market validation |
| **Champion** (functional lead) | Making the right call, career safety | Recommending something that fails or gets cancelled | Ease of adoption + speed to value + team adoption track record | Peer reference + implementation timeline data |
| **End user** | Workflow fit, ease of use | Added friction to their day | Time saved, simpler than what they use now | Product demo + user testimonials |
| **Technical evaluator** (IT, security) | Integration, security, compliance | Technical debt, security risk | API quality, integration library, compliance certifications | Technical documentation + security review packet + reference architecture |
| **Procurement / legal** | Contract terms, vendor risk, compliance posture | Signing a vendor that creates liability or fails an audit | Clear terms, data-handling and security certifications (SOC 2, ISO), vendor stability | Contract redlines history, security review packet, references from similarly regulated customers |

**Cross-stakeholder consistency rule:** each row uses a different entry point, not a different claim. All five rows must trace back to the same three pillars from Step 3 — the economic buyer's "revenue or cost impact" and the end user's "time saved" should both cash out as proof points under the same pillar, not as competing stories. If a stakeholder's key message can't be traced to a pillar, either the pillar set is incomplete or the stakeholder message is inventing a claim the rest of the platform doesn't support.

**Sequencing a multi-stakeholder deal:** lead with the row that matches who's in the room first — a technical evaluator brought in early gets the integration and security row before anyone shows them an ROI number. Don't lead every stakeholder with the economic buyer's message; that's the most common way a champion loses internal support for a deal they already believe in. Procurement and legal are the exception to "lead with who's in the room": they rarely surface early, but they kill more late-stage deals than any other stakeholder — map this row during discovery so it exists before it's needed, don't wait for it to become the blocker in the final contract review.

**Scale the map to the deal, don't map all five rows by default.** A self-serve or low-ACV motion rarely has a real procurement/legal stakeholder or a dedicated technical evaluator distinct from the end user — forcing all five rows onto that motion produces a filled-in template, not a useful one. Reserve the full five-role map for deals where a genuine buying committee forms (multiple distinct people, a formal evaluation, a contract negotiation); below that, the economic buyer and the end user rows usually cover the real committee, and the rest is exactly the kind of "framework filled in for its own sake" this document exists to avoid.
