# Sourcing and Running the Sequence in Bulldozer OS — Detail

**Turn the segmentation triggers into real signals, not a manual scan.** `bdzListSignalTypes` / `bdzCreateSignal` / `bdzListSignals` cover a confirmed catalogue that includes `JOB_OFFERS`, `JOB_OFFERS_WATCHLIST`, `RECRUITMENT_CAMPAIGN`, `REPUBLISHED_JOB_OFFERS`, `EMPLOYEE_DEPARTURE`, `COMPANY_GROWTH`, `DEPARTMENT_GROWTH`, and `COMPETITOR_RELATIONSHIP` — each with its own credit cost fixed at creation. The "job posting" and "new exec hire" triggers map directly onto the job-offer and departure types; "funding announcement" is closest to `COMPANY_GROWTH`/`DEPARTMENT_GROWTH`.

**The "tech stack change" trigger is now a confirmed mapping, with a real trap.** `TECH_ADOPTION` and `TECH_DISPLACEMENT` — two of the confirmed 32 signal types, among the three most expensive at 12 credits/lead — are the OS mechanism for it (a real call against `bdzListSignalTypes` has since read their config fields in full): symmetric pair, `TECH_ADOPTION` fires when a company starts using a tool, `TECH_DISPLACEMENT` when it drops one, which makes `TECH_DISPLACEMENT` the one that actually fits a competitive-displacement pitch. Both take `trackedTool` (an exact vendor name) or `trackedCategory` (a whole category), plus the usual firmographic filters, `targetPersonas`, and `dailyLeadLimit` (default 20). `AI_ADOPTION` shares the identical config shape but is a narrower, distinct signal scoped to AI-adjacent products (Claude/ChatGPT/Cursor and similar) — don't present it as a third generic tech-stack-change signal. **The trap:** `trackedTool` needs the exact spelling an external Lemlist/technographic-data endpoint would use, and no `bdz…` tool in the OS exposes a way to list or validate valid values — a misspelled tool name isn't rejected, it just silently returns zero leads (the same failure mode already known for `companyIndustries`). Before wiring this signal up, either get the exact name from somewhere else already in hand (e.g. a `detectTechnologies` enrichment result) or warn whoever's running it to double-check spelling outside the OS rather than promising a result.

**The 32 signal types are not priced the same — arbitrate on that before scanning a whole segment.** The confirmed `creditsPerLead` spread runs from 0.5 (passive social engagement types like `COMPANY_FOLLOWERS` or `SOCIAL_REACTIONS`) up to 12 for the three most expensive company-level types (`TECH_ADOPTION`, `TECH_DISPLACEMENT`, `AI_ADOPTION`) — a 24x spread, and that's a floor: optional enrichment booleans (`getEmails`, `getPhones`, `getSireneData`, `detectTechnologies`, `getHomepageContent`) add roughly +1 credit/lead each on top. Running an expensive signal across an entire segment to find a handful of qualified accounts burns budget for nothing — reserve the 7+ credit signals for a short list of already-tiered target accounts, and default to the cheap engagement signals (which is what the "LinkedIn post" trigger below already is) when scanning broadly.

**The "LinkedIn post about the pain you solve" trigger has a direct tool, not a scroll session.** `bdzCreateLinkedInPostListJob(profileUrl)` scrapes a profile's recent posts, comments, and reactions over a configurable window (default: last 3 months). Once it succeeds, `bdzListLinkedInPosts` reads the results back filtered by `minReactions`/`minComments` and sorted by reaction or comment count — pull the posts that actually got engagement, not just the newest ones. `bdzListLinkedInPostComments` and `bdzListLinkedInPostReactions` on a specific post return exactly who engaged with it: that list is your Touch 1 target, already warm. For a whole target account instead of one profile, `bdzCreateLinkedInEmployeeListJob` + `bdzListLinkedInEmployees` pull the company's people. If an account, a profile, or a post is worth watching over time rather than scraping once, `bdzCreateLinkedInRefreshConfig` schedules a recurring refresh (daily, weekly, or monthly) instead of re-running the job by hand.

**Qualify the resulting list the same way as any other outbound list.** Whether the names came from a signal or from post engagement, run them through `bdzCreateLeadList` / `bdzSourceLeadList` to populate, then `bdzUpdateLeadListLead` to move each one through `TO_REVIEW` → `ACCEPTED`/`REJECTED` with a note. Don't spin up a second, parallel list just because the source was LinkedIn.

**Multi-channel means one campaign, not two disconnected tools.** `bdzCreateLemlistCampaign` creates the campaign; `bdzListLemlistSequences` returns the `sequenceId` it auto-provisions; `bdzCreateLemlistSequenceStep` adds each touch with a `type`. The LinkedIn-specific types confirmed in the tool's own schema map directly onto this sequence's five touches: `LEMLIST_STEP_TYPE_LINKEDIN_INVITE` for Touch 1, `LEMLIST_STEP_TYPE_LINKEDIN_SEND` for the DM touches (2, 3 bridged as email instead uses `LEMLIST_STEP_TYPE_EMAIL`), `LEMLIST_STEP_TYPE_LINKEDIN_VOICE_NOTE` for Touch 4. The catalogue also has `_VISIT`, `_FOLLOW`, `_LIKE_LAST_POST`, `_COMMENT_LAST_POST`, `_ENDORSE`, and `_WITHDRAW_INVITATION` — useful for a lighter pre-touch warm-up (visit + follow before the connection request) if the account needs it, see the warm-up guidance below. `bdzCreateLemlistLead` needs an email or a LinkedIn URL (at least one) and takes up to 50 custom variables — that's the real mechanism behind "personalization at scale" above, not a name-merge tag. None of these tools write the copy: the message text stays the operator's job, produced from this file.

**Building the campaign isn't running it — `bdzStartLemlistCampaign` is a separate, real step, and it fails loudly if skipped carelessly.** It's a pure pass-through to the Lemlist API (no local state check before the call), and real client usage shows it failing 100% of the time on a campaign that's already running, with the exact message "You can't start campaigns that are already running." Treat that specific error as confirmation the sequence is live, not as a bug to retry. Before calling it, check status with `bdzListLemlistCampaigns` or `bdzGetLemlistCampaign` — but those read the OS's own stored copy, synced from Lemlist on an hourly cycle, not Lemlist's live state, so a campaign started or stopped in the last hour by another route may not show it yet.
