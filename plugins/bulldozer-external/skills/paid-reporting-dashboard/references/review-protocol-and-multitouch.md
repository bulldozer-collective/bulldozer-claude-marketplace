# Bi-Weekly Review Protocol and Multi-Touch View

**Cadence:** every two weeks, fixed on the calendar — not "whenever the numbers look interesting." Attendees: whoever owns paid budget, plus whoever owns the CRM attribution fields (Layer 2 and Layer 4 break silently when no one is watching them).

**Agenda, in this order:**

1. **Data integrity first (5 min).** Original Source match rate still above 80%? Any campaign showing 0 offline conversions where there should be some? Fix tracking before discussing performance — a scorecard built on a broken Layer 2 or Layer 3 produces confident, wrong conclusions.
2. **Scorecard review (10 min).** Walk the escalation bands table above. Anything in Investigate or Critical gets named; anything that crossed a band since the last review gets flagged even if it's still Healthy.
3. **Campaign-level drill-down (10 min).** For anything flagged in step 2, pull Dashboard 3. Decide: scale, hold, or kill — using the volume floor rule above before killing anything on thin data.
4. **Budget reallocation decision (5 min).** Only made using the 90-day or 180-day windows, never the 30-day one. The 30-day column exists to catch tracking breaks (a campaign with spend and zero pipeline after 30 days is a tracking problem, not necessarily a performance problem) — it is not a reallocation signal on its own.

**Why every two weeks and not weekly or monthly:** weekly pipeline reviews correlate with meaningfully better forecast accuracy than irregular ones in cross-functional GTM benchmarking (Ebsta × Pavilion, 2025 GTM Benchmarks Report) — but that data point is about pipeline forecasting cadence generally, not about ad-budget reallocation specifically, and no analyst source pins a cadence for this exact decision. Bi-weekly is the practical middle: frequent enough to catch a broken tracking layer before it wastes a month of spend, spaced enough that each review has new deals to look at rather than re-litigating the same three data points.

**Second view once volume supports it:** the single-touch `Deal Source` field (Layer 4) is the baseline every dashboard above is built on, and it should stay that way — it's simple enough that everyone in the room trusts it. Once a deal has enough multi-touch history to be worth the extra read, a multi-touch attribution report is a second view to sanity-check the single-touch story, not a replacement for it — Bulldozer OS can compute this against HubSpot (`get_campaign_attribution_reports`: linear, U-shaped, time-decay, or first/last-touch, scoped to closed-won deals), no export needed — multi-touch models split credit across touchpoints in a way that's genuinely useful for spotting influence you'd otherwise miss, but the split itself is a modeling choice, not a measured fact. **This one isn't a path you can promise unconditionally:** the tool fails outright with `Insufficient scope: required "marketing.campaigns.read"` on a portal where that scope hasn't been granted — this has been observed on a live call, not just read from the schema, and it blocks the whole report (every model), not just campaign-object fields. Call it once against a throwaway query before naming a specific attribution model in a client deliverable; if it fails on scope, tell the client's HubSpot admin which scope to grant rather than presenting this as broken, and fall back to Deal Source and the deal-level report in Layer 4 in the meantime.

Four traps in this tool's own contract, worth knowing before trusting its output over Deal Source: **(1)** the tool won't just answer on a cold call — the first call of a session must either read `tool_guidance` for `get_campaign_attribution_reports` first, or submit once and accept the round-trip: an unread call returns `status=READ_TOOL_INSTRUCTION_REQUIRED` with the real instructions attached rather than a report, and the retry needs `hasReadToolInstructions=true`. A request wide enough to be slow (a broad date range, two dimensions) doesn't return the report either — it returns `PROCESSING` with a `taskId` to poll. Neither of these is the `marketing.campaigns.read` scope failure above; they're separate failure modes, worth telling apart from a real block when this call sits inside an automated routine rather than a one-off check. **(2)** group by `REVENUE` (attribution-weighted) when comparing channels, never `DEAL_AMOUNT` — the latter is the deal's full value, deduplicated per deal, and grouping it by a non-deal axis like channel re-adds that full value under every channel that touched it; a cross-channel total on `DEAL_AMOUNT` reads higher than actual closed revenue, sometimes by a lot on deals with a long multi-touch history. **(3)** the date window doesn't anchor to the same field for every metric — close date for `REVENUE`/`DEAL_AMOUNT`, create date for `DEAL_COUNT`, the touchpoint's own date for `CONTACT_COUNT`/`ATTRIBUTION_COUNT` — so "last 90 days" pulled for two of these rows can describe two different sets of deals without either number being wrong. **(4)** the tool requires the contact to be associated to the deal *before* it closes; a contact attached after close-won — an ordinary late marketing-to-sales handoff, or a rep tagging the right contact weeks after signature — creates no retroactive attribution, only a manual deal↔campaign association counts regardless of timing. A channel that looks quiet in this report may just be one where credit keeps arriving through people associated too late to count — a process gap, not proof the channel isn't working.
