# Running Signal-Based Outbound in Bulldozer OS

## Mapping the 7 categories onto Bulldozer OS's signal catalog

**Where these map onto Bulldozer OS's own signal catalog.** `bdzListSignalTypes` (32 types) confirms two direct matches by name and config, not just by name. Job posting match runs on the OS's job-category types (job offers, job-offer watchlist, recruitment campaign, republished job offers). Tech stack change runs on a confirmed pair, `TECH_ADOPTION` and `TECH_DISPLACEMENT` (company category, 12 credits/lead — the catalog's most expensive tier alongside `AI_ADOPTION`): a live `bdzListSignalTypes` call reads their full config (`trackedTool` or `trackedCategory`, plus `companyEmployeeSizeRanges`/`companyIndustries`/`companyCountries`/`companyRegion`/`excludeDomains`, `targetPersonas`, `dailyLeadLimit` defaulting to 20), and the two are symmetric — adoption fires when an account starts using a tool, displacement when it drops one, so displacement is the real trigger for a competitive-switch pitch, not adoption. `AI_ADOPTION` shares the same config shape but is a narrower, distinct signal (scoped to Claude/ChatGPT/Cursor-type tools) — don't present it as a third generic tech-stack-change signal, it's built for vendors selling into that specific wedge. **Confirmed trap on all three:** `trackedTool` needs the exact name used by an external technographic-tools endpoint that no `bdz…` tool exposes (no `bdzList*TechnographicTools`/`Categories` exists) — a misspelled value isn't rejected, it silently returns zero leads. Get the exact name from somewhere else first (e.g. a `detectTechnologies` enrichment result) or warn whoever configures it to double-check spelling outside the OS, don't promise a result. Content engagement doesn't need a subscribed signal type at all — it has a direct one-call path via `bdzSourceLeadList`, also detailed below. First-party intent, funding event, new executive hire, and competitor mention aren't confirmed against a named OS signal type as of this writing — check the project's own `bdzListSignalTypes` output before assuming the OS covers them; if it doesn't, the external sources below still apply.

## Running This in Bulldozer OS

Everything above is tool-agnostic on purpose — the signal universe and scoring logic hold regardless of what fires the alert. Bulldozer OS has its own native path for the sourcing, tiering, and sequencing steps, and it's worth knowing before reaching for the third-party stack above.

**Signals as a first-class OS object, priced per lead, not per seat.** `bdzListSignalTypes` returns the project's live catalog — 32 types split across four categories (jobs, social, company, funding) — each with a `creditsPerLead` frozen at creation. The spread is wide: cheap social-engagement types (company followers, post reactions, influencer engagement) sit around 0.5–1 credit/lead, while the three company-level technology signals (tech adoption, tech displacement, AI adoption) sit at 12 credits/lead — 24× more per lead than the cheapest type. That number should drive which signal you start with, not the category's conceptual appeal: a wide, cheap social signal generates volume to tune your triage rules on; the expensive technographic ones are worth turning on only once routing and SLAs are proven. `bdzCreateSignal` provisions one (type + its config from `bdzListSignalTypes` + the `leadListId` it feeds — mandatory, a signal can't exist without a lead list to land in); `bdzListSignals` reads back what's live and its frozen cost. Five optional enrichment add-ons (email lookup, phone lookup, French SIRENE data, technology detection, homepage content) each add their own flat per-lead surcharge on top of the base `creditsPerLead`, on all 32 types — request them only when the sequence step actually needs the field.

**Content engagement has a direct, one-call path.** `bdzCreateLinkedInPostListJob` scrapes a profile's posts (async — poll with `bdzGetLinkedInPostListJob`, then read with `bdzListLinkedInPosts`, sortable by `orderBy=LINKED_IN_POST_SORT_FIELD_REACTION_COUNT` or `_COMMENT_COUNT`), so you can find which post on a target's profile actually generated engagement instead of guessing. Once you have that post's URL, `bdzSourceLeadList` with `type=LEAD_SOURCE_TYPE_LINKEDIN_POST_REACTION` and `linkedInPostReactionPostUrl` turns its reactors directly into leads in a chosen lead list — no separate signal subscription needed for a one-off pull. For a standing watch on a specific company, person, or post rather than a one-off pull, `bdzCreateLinkedInRefreshConfig` (`targetType=COMPANY|POST|PEOPLE`, `periodicity=DAILY|WEEKLY|MONTHLY`) re-scrapes it on schedule — but each config watches exactly one URL, so it's a per-account watch, not a Sales-Navigator-style saved search across a whole ICP list; watching 200 accounts means 200 configs, not one.

**Tiering lives in a note, not a score field.** The OS has no numeric lead-score column: `bdzUpdateLeadListLead` carries a free-text `note` (2000 characters) and a review `state` (`TO_REVIEW` / `ACCEPTED` / `REJECTED`) per lead-per-list. The scoring matrix above has to be encoded into that note (e.g. "Tier 1 — funding + exec hire, score 82, fired 2026-09-03") for a human or a downstream export to read the tier back — there's no field the sequence tool can branch on automatically.

**The sequence itself runs on Lemlist.** `bdzCreateLemlistCampaign` (name only) provisions a campaign with a default sequence — read its `sequenceId` with `bdzListLemlistSequences` before adding steps. `bdzCreateLemlistSequenceStep` (campaign + sequence + `type` + `delay` in days, 0–1500) builds the touch sequence per tier from the tables below — step types include email, LinkedIn invite/visit/send/voice-note/comment, phone, SMS, and WhatsApp, so a Tier 1 multi-channel sequence is one campaign, not three disconnected tools. `bdzCreateLemlistLead` adds each qualified lead (email or LinkedIn URL — a LinkedIn-only lead from a post-reaction pull needs no email enrichment to enter the sequence) with up to 50 custom `variables`, which is the real mechanism for the "unique message angle per signal type" rule below: pass the signal type, the tier, and the specific fact (which post, which round, which JD line) as variables, reference them as `{{variable}}` in the step copy, and the same campaign serves every signal type without becoming a generic template with a name token swapped in. `bdzStartLemlistCampaign` launches it — check `bdzListLemlistCampaigns`/`bdzGetLemlistCampaign` first: it's a pass-through to the Lemlist API with no local state check, so calling Start on a campaign that's already running fails every time with Lemlist's own "You can't start campaigns that are already running," and the two list/get reads are themselves a snapshot synced hourly, not the live Lemlist state, so a check made right before a fast re-trigger can still miss a change from inside that hour. None of this writes the copy — the message angles below are still the operator's job — the tooling only gets the qualified, tiered, contextualized lead into a running sequence without a manual handoff.
