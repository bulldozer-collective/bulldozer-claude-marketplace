# Grounding the Draft in Bulldozer OS

## Grounding the draft in Bulldozer OS

If this client's project is set up in Bulldozer OS, several sections below don't have to start from a blank page or a guess at the codebase — the OS may already hold a project-level analysis for them. Check before drafting by hand, and always present what comes back as a starting point to confirm with the client, not as a finished section — these are directional analyses, not verified facts. And for three of the four analyses below, "what comes back" isn't a single value: their key text fields carry the AI's own read plus a separate slot for whatever the client corrected afterward. Read the client's correction when one exists — pulling the AI's superseded first guess instead would put back into the draft exactly the sentence a past engagement already told you was wrong.

- **Target Audience, Objections & Anti-Personas**: the OS can hold a declared set of ICP profiles — targets, anti-personas (who to actively decline), prescribers, and blind spots (segments the offer fits but nobody talks about). A blind spot is worth surfacing on its own even if the client didn't ask for it. This one is a plain read, no client-correction layer to check.
- **Differentiation, Proof Points**: if a value proposition analysis exists for the project, it returns each claimed value proposition — marked primary or secondary — with its own proof, plus a separate list of claimed differentiators. Use it as the first draft of these two sections instead of re-deriving them from the site. Its summary and pricing text, and its own note, each come back as the AI's draft plus an optional client correction — show the correction when one exists. The value-proposition and differentiator lists themselves don't carry that two-sided structure: what comes back there is always the analysis's current read.
- **Competitive Landscape**: a market-positioning analysis (if one exists) places the company and its rivals on two labeled axes with a sourced justification for each — a stronger starting point for "how each falls short" than a description written from memory. Its axis labels and synthesis note follow the same draft-plus-correction pattern as the value proposition above; each rival's actual position on the map (the two coordinates and its own justification) doesn't, so that part is always the analysis's latest read. An offer-structure analysis, where available, adds a market-concentration verdict (monopoly through atomized — how many players hold the top spots) and a short list of competitor categories; the verdict's justification text is itself another instance of the same draft-plus-correction pattern, check for a client override there too before quoting it. That verdict is a pure concentration scale, not a maturity read: don't stretch it into calling the market "emerging" or "declining," that's a separate judgment call to make with the client, not something this analysis measures. Treat any competitor revenue or headcount figures that come back with this as rough, publicly-sourced estimates — never repeat them to the client as verified numbers. And don't lock a specific rival's name or quadrant into the document as a permanent fact — this analysis is recalculated on every run; re-check it rather than assuming last quarter's read still holds.
- **Brand Voice**: if a tone-of-voice configuration is already stored for the project, use it rather than inventing a voice — it typically carries the intended tone, personality keywords, and often an explicit list of words the brand has decided never to use. Also a plain read, no correction layer here.

None of this is guaranteed to exist for a given project — these are project-level analyses that have to have been run first, and some need prerequisites of their own (a tracked competitor, a completed value-proposition pass) before they'll return anything. If a check comes back empty or the project isn't in Bulldozer OS, drop back to Step 1's other two options for that section — don't block the draft waiting on an analysis nobody has run.
