# Sample Ratio Mismatch (SRM) check — detail

Before reading the metric, check the split. Compare the actual visitor count per variant against the configured allocation (a 50/50 test should land close to 50/50) with a chi-square goodness-of-fit test — [Evan Miller's chi-squared calculator](https://www.evanmiller.org/ab-testing/chi-squared.html) runs this without a spreadsheet.

A mismatch significant at p<0.01 — deliberately stricter than the test's own 95% threshold, because the cost of missing this is higher than a normal false positive — is a Sample Ratio Mismatch (SRM): a bucketing or logging bug (asymmetric redirects, uneven bot filtering, a tag that fires late on one variant) that invalidates every other number the test produced, no matter how clean the primary metric looks.

Run this check first, every time; a clean SRM check doesn't prove the test is trustworthy, but a failed one proves it isn't. Optimizely flags SRM automatically while the test runs, but not by re-running this same chi-square check on a timer — it uses a dedicated sequential method (what it calls "sequential sample ratio mismatch"), built precisely because checking a point-in-time chi-square test repeatedly while data accumulates has the same peeking problem as checking a p-value early. Don't assume every platform that advertises "automatic SRM detection" uses the same method or avoids that peeking problem; check what it actually runs. No confirmed native SRM detection was found for Convert at time of writing — only a third-party browser extension that checks several platforms' counts from the outside — so don't cite it as a built-in feature without checking Convert's own docs first.
