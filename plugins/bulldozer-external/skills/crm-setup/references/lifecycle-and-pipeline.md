# Lifecycle Stages and Deal Pipeline Details

## 1.1 Lifecycle Stage Configuration (HubSpot)

**Check first whether Sales Hub's native LEAD object is turned on for this portal — it runs alongside `lifecyclestage`, not instead of it, and the mapping below only covers one of the two.** LEAD is a separate first-class CRM object (distinct from Contact), confirmed live on a real HubSpot portal: it carries its own pipeline, with a fixed top-level status (New / In Progress / Qualified / Unqualified) and fully custom concrete stages inside it — the portal audited for this doctrine had built five retry stages for a "didn't pick up" cadence under In Progress, ahead of Recontacter and Qualified/Disqualified, not whatever a fresh install ships with by default. A reporting or automation tool that can already see the object in the portal's schema can still fail to read a single LEAD record: it requires the `crm.objects.leads.read` scope, which isn't granted by default even once the object itself is visible — re-authorize the connection before promising anything built on LEAD data. Build the `lifecyclestage` mapping below regardless (every portal has it); treat LEAD as a second, independent qualification mechanism to check for on any Sales Hub portal, never assumed absent just because this skill's mapping doesn't mention it.

The native `lifecyclestage` property ships with 8 options at install: Subscriber, Lead, Marketing Qualified Lead, Sales Qualified Lead, Opportunity, Customer, Evangelist, Other. Six of those are used below and don't need to be renamed — their definitions still need to be documented and their triggers built into workflows. **SAL (Sales Accepted Lead) is not one of the 8 native options** — it's a common enough addition that most B2B teams add it, but it has to be created as a new picklist value on the property (Settings → Properties → Lifecycle Stage → Edit → add option) before any workflow can set it, or the stage will silently fail to save:

- Subscriber: form fill, unknown company
- Lead: company data enriched + ICP match at firmographic level
- MQL: meets lead score threshold (build this in Phase 3)
- SAL *(custom addition, not native)*: SDR marked "Accepted" in contact record
- SQL: discovery call held, deal created with minimum required fields
- Opportunity: deal created (auto-synced from Deal lifecycle stage)
- Customer: Closed-Won deal (auto-synced)

Evangelist and Other exist natively too but aren't used by this sequence — leave them on the property, don't delete them; a deleted picklist value cannot be reliably reconstructed on records that already used it.

**Skip creating the SAL value entirely if the same person sources and closes the deal.** SAL exists to create accountability at a handoff — it only earns its keep when the SDR marking "Accepted" and the AE working the deal are different people. On a team where one rep does both jobs, that's the same person accepting their own handoff: a stage nobody advances deliberately, a workflow to maintain for no report anyone reads, and an extra transition in 3.2 that just delays SQL for no reason. Go straight from Lead to SQL until the roles actually split, then add SAL back — creating the picklist value later costs nothing; building and then ignoring it for months costs a habit of stages nobody trusts.

**Build a lifecycle stage definition document** (1 page) before configuring anything. Paste it into a pinned Slack channel so every rep can reference it.

## 1.2 Deal Pipeline (HubSpot) — required-field pitfalls

**A required text field is a box, not proof.** Setting economic buyer name and champion name as required fields stops a rep from advancing a deal with the field blank — it does nothing to stop a rep under pipeline pressure from typing a plausible name pulled off LinkedIn to get past the gate. The field being full tells you the rep complied with the setup, not that anyone has actually been in a room with a person who can sign. Two configuration choices make the field closer to real proof instead of a checkbox: pair it with a note field asking for one piece of evidence (a quote, an email thread, a meeting the rep actually attended), and separately, once deals are flowing, watch `num_associated_contacts` on deals sitting in Proposal or Negotiation — HubSpot fills this automatically as contacts get associated, and a deal at 1 several weeks into late stage is a single-threaded account regardless of what name is typed in the champion field. Neither replaces manager judgment on a live deal; both make it harder for a filled-in field to substitute for one.

**A native field tags who's who, ahead of any text the rep types from memory.** HubSpot's `hs_buying_role` (Contact property, multi-select enum — confirmed live on a real HubSpot portal: Blocker, Budget Holder, Champion, Decision Maker, End User, Executive Sponsor, Influencer, Legal & Compliance, Other) exists to record the exact distinction the champion/economic-buyer text fields are trying to approximate. It lives on the Contact, not the Deal — a contact who is Champion on one deal and just an Influencer on another can't hold two different values on this one field at once; where that split matters, the deal-scoped answer is the Contact-to-Deal association label, or Buying Groups (Sales Hub Professional+), not this property. Cheaper to check than waiting for the 1-on-1 pipeline review: if none of a deal's associated contacts carries Decision Maker, Budget Holder, or Executive Sponsor, there's no economic buyer on this deal yet regardless of what name sits in the required text field.

**HubSpot's native "Closed Lost Reason" (`closed_lost_reason`) is a free-text field, not a picklist — confirmed live on a real HubSpot portal.** There's no built-in list of options to curate; requiring it as-is just forces every rep to type something, and a free-text "reason" is worse for reporting than a bad picklist, because it can't be rolled up at all ("budget," "Budget issue," "no budget" are three different strings). Build a dedicated custom property instead — a real enum, e.g. `deal_lost_reason`, with a closed set of options a rep can actually attribute a specific deal to — and require that one, not the native field. Review the distribution after the first full quarter of real losses and split whichever option is quietly absorbing more than its share. **Migration note:** if this is a migration from an existing HubSpot portal that already used the native text field, don't convert it to a picklist in place — HubSpot blocks entering already-closed deals that carry old free-text values once the field becomes a picklist, so every historical Closed Lost deal ends up looking required-and-empty. Build the new custom enum property alongside the old one instead, and leave the legacy text field as read-only history.

**The "competitor field" required at Negotiation above has the same free-text trap, and HubSpot ships no dedicated property for it either — confirmed live on a real HubSpot portal.** There's no native picklist naming known competitors to attach to a deal: a portal audited for this doctrine turns up only a custom property built after the fact for the *losing* competitor, and it's free text with zero options — the same rollup problem as an unstructured Closed Lost Reason, just for competitor names instead of loss reasons ("Salesforce," "salesforce.com," "SFDC" don't group into one filter). Build a dedicated `competitors` property as a multi-select picklist (checkboxes) against the named competitors already tracked in the CRM strategy doc, not a text box — that's what lets a quarterly pull ("every deal we lost to Competitor X last quarter," see battlecards / win-loss-analysis) run as a clean filter instead of a text search across three spellings of the same company name.
