# Layer 4: Audience Strategy Checks

**Meta**
- Audience overlap: are Lookalikes, Interests, and Broad running side-by-side inside the same objective? This causes internal auction conflict
- Customer Match lists: uploaded, fresh (updated within 90 days), segmented by value tier? Generic "all customers" list is weak seed data
- Retargeting windows: 7-day and 30-day website visitors separated? 180-day is too broad for most businesses
- Advantage+ Audience vs. manual lookalike: since Meta folded lookalike targeting into Advantage+ Audience (the Andromeda update, live since late 2024), a standalone Lookalike ad set mostly re-derives what Advantage+ already infers from the pixel on its own — it earns a separate ad set only when its seed holds something the pixel has never seen (a CRM list, offline conversions, an LTV-weighted customer list). Flag a manual lookalike running on a plain purchaser/visitor seed as redundant with Advantage+, and document which of the two is actually active and why whenever both are present
- Read the actual targeting configured on an ad set with `bdzGetAdLayer2` rather than trusting the client's memory of what's running — note that Bulldozer OS reads this, it does not write it: no audience list upload, no lookalike/predictive seed, no offline conversion push happen through the OS. Every fix this layer produces gets executed directly in Ads Manager

**Google**
- Audience signals in PMax: high-intent seed (past purchasers, site converters) vs. generic site visitors? Generic = slow learning
- RLSA active on Search campaigns? Returning visitors convert 2–3x better — bid modifiers or dedicated campaigns
- In-market audiences layered on observation? Check performance after 30 days — if 20%+ above baseline, bid up or isolate. Google Ads Search carries a native per-audience bid modifier for exactly this — distinct from the device-only bid adjustment (mobile/tablet/desktop) — so this doesn't require duplicating the campaign by tier the way LinkedIn does. Read what's already attached with `bdzListSeaAdGroupAudiences`: its `observation` field is shared by every audience on the ad group (true = bid-only, false = restricts who sees the ad) — the first thing to check when impressions collapse right after an audience gets added. Setting the bid itself always forces observation mode as a safety net, so it can only ever adjust bids, never restrict delivery — "isolate" still means a separate campaign, not this mechanism
- Customer Match list size: the minimum was lowered from 1,000 to 100 users across all networks including Search (generalized 2024–2025). A seed that would have been dismissed as too small two years ago — a closed-won list, a single webinar's attendees — may be usable today; don't apply the old 1,000-user floor when reviewing what a client already has on hand. Meeting the 100-user floor once isn't enough to keep serving: converging sources (not a support.google.com page read directly — same egress block noted elsewhere in this audit) describe a rolling eligibility check that needs at least 100 members added or updated within roughly the last 540 days. A list built once and never refreshed can quietly age out of eligibility long before anyone notices it stopped serving — check upload recency, not just current size, before trusting a list that's been sitting untouched

**LinkedIn**
- Predictive Audiences (AI-built from a first-party source — a contact list, Lead Gen Form submissions, or Online Conversions) replaced classic Lookalike Audiences, retired in 2024: minimum seed around 300 members. The per-account cap on Predictive Audiences themselves is not settled — sources disagree, and disagree more with each search: 30 and 100 have circulated for months, and a newer source now cites 200, with no official LinkedIn or Microsoft Learn page reachable to arbitrate any of them. Don't quote any of the three numbers as fixed — check the actual account in Campaign Manager. Since August 2026 there's also an account-wide ceiling of 1,000 total DMP segments — Matched Audiences and Predictive Audiences combined, expired and archived ones included. It's a hard cap (new segment creation is refused once hit), not a soft warning, and it doesn't touch segments or campaigns already running — only the ability to create more. An account that leans on both audience types can hit this ceiling well before the Predictive-Audience cap even becomes relevant, so an audit that finds delivery stalling on audience creation should check total segment count first, not just the Predictive count
- Audience Expansion (broadens delivery toward demographically similar profiles, on by default, unrelated to Matched Audiences) turns itself off automatically the moment a campaign uses a Predictive Audience — the two never stack. Document which one is actually driving delivery, not which one is toggled on
- Pull the real targeting with `bdzGetAdLayer2` rather than trusting the client's recollection — but its `audience` field is a best-effort projection re-synced from Campaign Manager on each import, not necessarily current. A targeting facet LinkedIn supports but Bulldozer hasn't modeled won't show there; it's still in `targetingCriteriaRaw` (LinkedIn's verbatim targeting, the source of truth), and `audienceSyncedAt` only dates the last check, not the last change — an empty `audience` next to a recent sync timestamp proves nothing
- **Configured targeting is not who was actually reached.** `bdzGetAdLayer2`'s `audience` field only says what was set up — `bdzGetAdDemographicAnalytics` (job title, function, seniority, company, industry, size, country, region) reads who the ads actually delivered to, live from LinkedIn. It never reconciles with `bdzGetAdAnalytics`: LinkedIn caps each breakdown at the top 100 values per creative per day, drops any segment under 3 events, and doesn't adjust cost for over-delivery — summing a breakdown's rows to check against the account's total cost or impressions doesn't verify anything, it structurally undercounts. Two more limits worth knowing before promising a client a demographic answer: only 2 years of retention (against 10 for performance data), and a 12–24 hour read delay, never real time. Useful whenever the seniority or job-title mix looks wrong for the ICP, or to confirm an audience edit actually shifted who gets served rather than just the audience field on record
