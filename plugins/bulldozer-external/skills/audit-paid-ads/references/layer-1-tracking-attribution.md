# Layer 1: Tracking, Privacy and Attribution Checks

### Account & Page Access
- Before trusting anything pulled below, confirm the account can actually be read (and, where a fix will require writing, written to). `bdzCheckAdAccountAccess` returns three independent verdicts — `readAccess`, `writeAccess`, `pageAccess` — each `GRANTED`/`DENIED`/`UNKNOWN`, never one combined status. `pageAccess` names a failure pattern this audit sees often and had no explanation for until now: a campaign and an ad set create without error, then the creative fails — because publishing a creative is the step that runs under the Facebook Page or the LinkedIn Organization, not the two layers above it. `DENIED` is a confirmed platform refusal (Meta error codes 200–299, error 10, or subcode 33; LinkedIn 403) and never appears alone on `readAccess`/`writeAccess` — a refusal on the account itself always denies both together. `UNKNOWN` never means refused: it covers no token stored, an expired token, rate limiting, a platform outage, or a LinkedIn 404 that reads equally as "account inactive" or "invisible to us" — the check can't tell those apart. Microsoft Advertising has no check implemented for this tool at all, despite being one of the four platforms the OS integrates — never expect this diagnostic on a Microsoft account. Run it before telling a client to just retry a failed Meta or LinkedIn creative: a `pageAccess` of `DENIED` needs the Page or Organization re-shared with the ad account, an `UNKNOWN` needs a retry later or a reconnected token — treating either as the other burns a cycle for nothing.

### Conversion Tracking
- Are conversion events firing accurately? Check for duplicates, missing events, test event fires
- Primary conversion action is a real business outcome (purchase, qualified lead, trial start) — not a click or page view
- On Google: which conversions are marked Primary vs. Informational? Verify this is intentional
- On Meta: which event is each campaign optimizing for? Is it the right one for the objective?
- On LinkedIn: does a `WEBSITE_CONVERSIONS` campaign actually have a conversion rule linked? `bdzListAdLinkedInConversions` reads the rules already set up in Campaign Manager (Insight Tag or Conversions API, including ones shared from the same Business Manager) — the rule's `originId` is what has to be passed into `linkedIn.conversionIds` on the campaign (`bdzCreateAdLayer2`/`bdzUpdateAdLayer2`). Bulldozer has no tool to create the rule itself, only to read and link it. A campaign launched without that link measures nothing and gives no warning that anything is wrong — no error, no 400, just a permanent zero in the conversion column until someone notices. Check this before trusting any LinkedIn conversion count in this audit, and treat a rule read back with `enabled: false` as deleted in Campaign Manager — a `conversionIds` still pointing at it is a configuration to flag, not to reuse.

### Server-Side & Privacy Infrastructure
- Meta CAPI implemented? Check Event Match Quality (EMQ) in Events Manager, scored 0–10 per event — a low score means fewer events can be matched to a real Meta user, which starves the algorithm regardless of volume. Meta doesn't publish an official "good" threshold, but 2026 practitioner guides converge on a usable working range: below 6 is a tracking gap worth fixing first (server-side/CAPI, missing match keys), 6–8 is workable with room to improve (email, preserving click IDs), and above 8 is solid — don't chase 9–10, the marginal gain there is small. Treat this as a repère, not a Meta-published fact, and weight a score that sits well below the account's other events more than the absolute number
- Google Consent Mode V2 active if operating in EU/UK? It has been a compliance requirement there since March 2024, but the account-level penalty (loss of personalized ads, remarketing, and conversion tracking — not just a warning) only started actually being enforced on July 21, 2025: an account that looked fine on paper before that date can have been silently degraded since. Since June 15, 2026, `ad_storage` is the sole consent signal gating GA4-to-Google-Ads ad data — before that date the Google Signals setting could act as a fallback when `ad_storage` was missing; convergent trade coverage (not a Google page read directly — support.google.com stayed unreachable from this environment) says it no longer can, and Google Signals is now reporting-only. A site whose consent banner doesn't correctly set `ad_storage` loses conversions, audiences, and Smart Bidding signals silently, with no fallback net left. Enhanced Conversions enabled?
- Bounce rate on landing pages above 70%? In GA4 a session only bounces if it fails all three: under 10 seconds, no conversion event, no second page/screen view — that 10-second engagement threshold is configurable per data stream (up to 60s). A bounce spike that lines up with a config change (threshold edited, client-side tag broken) is the first thing to rule out before blaming the page
- Offline conversions flowing back to Google/Meta? If not, smart bidding is optimizing on incomplete data. If the fix on the table is wiring up Google Ads offline conversion import from scratch, check the account's history before recommending the classic click-conversion upload path (gclid/gbraid/wbraid against an UPLOAD_CLICKS conversion action): Google closed it to any account that hadn't already used it between December 2025 and May 2026 — a first-time call now gets rejected outright. The current path for a new setup is the Data Manager API (launched December 2025) or Enhanced Conversions for Leads; a standard CRM connector (HubSpot, Salesforce) doing this under the hood is unaffected either way. Even a grandfathered account doesn't get to keep this path indefinitely: converging trade coverage (Google's own developer blog cited, not read directly — same egress block as elsewhere in this audit) points to a full retirement of the legacy click-conversion-upload path in March 2027, for every account including ones already using it — worth flagging now as a longer-term migration item, not just a blocker for new adopters

### Attribution
- Attribution model consistent across platforms? Each channel claiming the same conversion = inflated reporting. On Google Ads specifically: as of September 2026 only two models are selectable — data-driven (default) and last-click. Google retired first-click, linear, time-decay, and position-based mid-2026 and auto-migrated any conversion action still set to one of them (to data-driven where the account has the volume to qualify, to last-click otherwise), no opt-out. A report or a client conversation that still names one of the four retired models is describing a UI that no longer exists. GA4 dropped the same four models even earlier (November 2023) and defaults to Data-Driven Attribution too, but the two platforms no longer gate DDA the same way: Google Ads dropped its own eligibility threshold (previously ~300 conversions + 3,000 interactions/30 days) in 2026 — DDA is now the default for every conversion action regardless of account volume, with only a performance recommendation left (~200 conversions + 2,000 interactions/30 days on supported networks, not a blocking floor). GA4 kept a stricter, hard gate: 400 conversions for the action AND roughly 20,000 conversions for the property within the lookback window — below that, GA4 falls back to last-click silently, with no warning anywhere in the UI. Both figures are conversions, not interactions or clicks: earlier synthesis of this threshold left the unit ambiguous, but converging sources now settle on conversions for both numbers — still not confirmed by a Google page read directly in this audit's own research, so treat the ~20,000 figure as directional rather than exact. If the GA4 channel report and the Google Ads account suddenly disagree on which campaign gets the credit, check GA4's own volume against that 400/20,000 gate (Admin → Attribution settings) before calling it a tracking bug — a credit shift can be this silent fallback, not a broken tag. Before recalculating that shift by hand period-over-period, check whether the OS already flagged it: any GA4 report already run through Bulldozer OS carries an automatic anomaly detection alongside its numbers — the lightweight `hasAnomaly` flag on every summary from `bdzListGoogleAnalyticsReports`, and full deviation detail (beyond 2 standard deviations from history) on the single report via `bdzGetGoogleAnalyticsReport`. A second, distinct cause to rule out for any shift dated around April 2026: converging trade coverage (again not a Google page read directly) describes Google recalibrating data-driven attribution that month, resetting some properties back onto the DDA model even where a different one had been manually selected — check Attribution Settings for whether the model itself was reset before assuming the volume gate is what moved.
- MER (Marketing Efficiency Ratio = Total Revenue / Total Ad Spend) calculated independently of platform-reported ROAS? Revenue comes from the CRM, spend from the platforms — never mix the two into one blended export. Pull spend per platform with `bdzGetAdAnalytics` (Meta/LinkedIn) or `bdzGetSeaL1Metrics` (Google) rather than asking the client for a manual total. Two precision traps specific to `bdzGetAdAnalytics`: it defaults to a 180-day lookback when `from`/`to` are omitted, so an unqualified pull reads a CAC smoothed over six months — pass `from` explicitly (e.g. 30–60 days) to read current performance, or a CAC that's degrading right now hides inside a stable-looking average. And for Meta, never sum `conversionsPerType` into the total: it lists upper-funnel events (view_content, add_to_cart, initiate_checkout…) *in addition to*, not instead of, the terminal events already counted in `conversions` — summing both inflates the conversion count and understates the true cost per result. A third field, `custom_pixel_events`, is a separate trap of the same kind: an unnamed aggregate the tool falls back to when it can't recover the individual names of the account's custom pixel events, also excluded from `conversions` because it overlaps the named entries — never add it into a total either, even when it looks like it's measuring an upper-funnel step the named breakdown missed. A fourth trap runs the other way: `conversions` is an upper bound, not just an underestimate, when a custom pixel event fires alongside the standard event it actually duplicates — Meta exposes no link between the two, so both get counted (observed at roughly 0.3–2.9% of the total). Rare, but real: don't assume every gap between platform-reported conversions and CRM-confirmed revenue is Meta under-counting.
- UTM structure consistent across all campaigns? Missing UTMs = dark traffic in GA4. Never put UTM parameters on an internal link (nav, footer, a CTA pointing to another page on the same site): a visitor who clicks it gets silently re-attributed to that UTM's source/medium, and the pollution becomes permanent the moment the tagged URL gets copied or shared elsewhere — track an internal click as a GTM event instead, and for a genuine multi-domain funnel use cross-domain measurement plus the referral exclusion list, never a UTM. If the client's CRM is HubSpot, multi-touch attribution by UTM/campaign/deal is available natively (see the data expert's audit-crm-tracking or attribution-funnel skill) — don't rebuild it from scratch in a spreadsheet
