# Where Health Score Data Lives, Dimension by Dimension

## Where This Data Actually Lives (dimension by dimension)

None of the six dimensions live natively end to end in Bulldozer OS — this is a customer-success model, and Bulldozer OS is a growth and marketing operations layer, not the client's own product. Map each dimension honestly before promising a CSM a live dashboard:

- **Product telemetry (35%, the biggest weight)** — the OS does not instrument in-app usage. Its GA4 and CMS reporting tools measure marketing-site traffic and form activity, not what a customer does inside the product after signup. This dimension has to come from the client's own product analytics (Amplitude, Mixpanel, Segment, or a data warehouse) — say so up front rather than implying the OS covers it.
- **Executive relationship (20%)** — the champion-tracking half is real: the OS can search and store a company's LinkedIn employee list on request and re-list it later. That makes "track job changes via LinkedIn" a schedulable habit instead of a CSM manually checking profiles — but it's an on-demand search job, not a live alert, so it only shows what changed since the last time someone re-ran it. The OS also runs "Job Changes" and "Employee Departures" as lead-generation signal types, but both are open-market discovery filters (job title, company size, industry, location) with no field to scope them to one named company — they surface moves anywhere matching the filter, not a specific existing account's champion. Don't propose them as an upgrade path to a live per-account alert; the on-demand re-run above is the only account-level option the OS actually has today. Knowing who currently holds which role is a separate question from catching when someone leaves: HubSpot's native `hs_buying_role` field on the Contact object (a 9-value enum — Blocker, Budget Holder, Champion, Decision Maker, End User, Executive Sponsor, Influencer, Legal & Compliance, Other; multi-select) tags each contact associated with the account, so a CSM can pull who's tagged Champion or Executive Sponsor before a QBR instead of inferring it from a job title. It's scoped to the Contact, not the account or a specific deal — a contact active on two accounts can't carry a different role on each — the deal-scoped equivalent is the Contact:Deal association label, or the Buying Groups tool (Sales Hub Enterprise). The table's third signal, executive-level NPS, isn't where it looks like it would be: Company and Contact carry no native NPS or CSAT field at all. The real signal sits one level down, on the Ticket object (`hs_last_nps_survey_comment`, `hs_last_csat_rating`, `hs_last_csat_date`, `hs_last_csat_comment`) — tied to a support interaction, not the account directly, and holding only the most recent value with no history to trend. Feeding it into a composite score means rolling it up across the account's tickets, not reading one property; it also points to an underlying Feedback Submission object that isn't itself a queryable type on every portal, so confirm both the ticket fields and the connector's read access before promising this as a live input.
- **Commercial signals (15%)** — check the subscription object first: on a portal that bills through HubSpot's own Commerce Hub, `SUBSCRIPTION` carries `hs_recurring_billing_end_date` (the renewal date itself) alongside `hs_status`, `hs_next_payment_due_date` and `hs_recurring_billing_frequency` — and it doesn't depend on the separate Contracts object being active, which makes it the more reliable first read on most Commerce Hub portals. The company object also carries two native rollups built for the same purpose, `hs_next_renewal_date` (earliest renewal date across all active contracts, auto-computed) and `hs_num_active_contracts`, but both roll up from Contracts specifically and stay empty or at zero on a portal that runs Subscriptions without also running Contracts. And on a portal that manages renewals purely through the deal pipeline (pipeline, stage, close date) instead of either Commerce Hub object, none of this carries real data. Check which pattern the client's portal actually uses (`get_properties` on the company and subscription objects) before assuming any of the three exists — the same caution that applies to deal-stage probabilities, which drift from the installer defaults on every portal that's actually been used.
- **Engagement pulse (15%)** — CSM outreach and response tracked through HubSpot's one-to-one email object, and QBR call quality through Claap recordings tied to the account, when both are connected to the project.
- **Support and success (10%)** — HubSpot's ticket object is queryable for teams on Service Hub — confirm the connector's read access on the client's own portal rather than assuming it, since that scope varies by client.
- **Financial health (5%)** — payment and invoicing behavior lives in the client's billing system (Stripe, Chargebee, or HubSpot's own billing where used), not in Bulldozer OS. When the client bills this account through HubSpot's own Commerce Hub, the subscription object's `hs_arr`/`hs_mrr`/`hs_status` give this account's real revenue trajectory since signature — pull it instead of reconstructing the account's value from memory or from the deal amount at signature, which goes stale the moment a contract changes.

**Writing the score back into the CRM is a separate access check from reading it.** The Output section above lists "a CRM-native approach" as one implementation path — in practice that means writing the composite score, RAG status, or a dimension value onto a HubSpot contact or company property so it routes automatically. Bulldozer OS's HubSpot connector tracks read and write access separately per object type, and CONTACT/COMPANY write commonly sits behind a reauthorization the connector doesn't have by default, even where read access already works fine (confirmed on the connector used to write this skill: both CONTACT and COMPANY show `read: AVAILABLE` / `write: REQUIRES_REAUTHORIZATION`, and the write tool itself is listed as a "potential tool" pending that reauthorization). Check that write access is actually granted on the client's own portal before promising a property that routes a red account to its owner automatically — if it isn't, report the score instead (a scheduled export, a Slack alert) rather than describe a write the connection can't currently make.
