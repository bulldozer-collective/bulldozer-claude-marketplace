# Pipeline Health Dashboard — Metrics, Forecast Checks and HubSpot Notes

## Pipeline Health Dashboard

| Metric | Definition | Target |
|--------|-----------|--------|
| MQL → SAL conversion | % of MQLs accepted by sales | >70% |
| SAL → SQL conversion | % of SALs qualified via discovery | >40% |
| SQL → Opportunity conversion | % of SQLs with opportunity created | >80% |
| Average opportunity age by stage | Days in each stage | Track, flag outliers |
| Pipeline coverage | Pipeline value / quota | 4–6x, or 1 / win rate — see note |
| Weighted pipeline | Stage-adjusted pipeline vs. quota | >1.2x |
| Closed won rate | Opportunities closed won / total closed | >25–35% |

**Forecast accuracy**: Track predicted vs. actual close rate by rep. Reps with consistently optimistic forecasts need coaching on stage definitions, not just pipeline size. Don't read a rep's forecast-accuracy variance from a period where too few deals closed — a 40% miss on three deals is noise, the same miss on thirty is a pattern; if a pipeline hasn't closed enough volume in a quarter to tell which, say so instead of coaching on it.

**If the CRM is HubSpot, check all three forecast fields before diagnosing a miss — they're independent and drift separately.** `hs_deal_stage_probability` (the per-stage, per-pipeline probability discussed above) is one signal. `hs_manual_forecast_category` — a category each rep sets on the deal themselves (Not forecasted / Pipeline / Best case / Commit / Closed won) — is a second. `hs_forecast_probability` is a *third*, separate numeric field: a rep can type a custom percentage into it without touching the category or the stage, so it can silently diverge from both. A forecast can be accurate at the stage-probability level and still wrong at the Commit/Best-Case level if reps never touch the categorical field, or the reverse — and a rep-entered probability can drift from both without anyone noticing unless someone checks it directly. An audit that only checks stage-probability drift is reading a third of the mechanism.

**Before diagnosing which is broken, settle which one the room actually means by "the forecast."** Whichever mechanism that turns out to be, check it on its own terms: (a) if the weighted number is off but the categories themselves are used consistently, that's a calibration problem — fix the probabilities or the category-to-percent mapping; (b) if deals sit in "Pipeline" for the whole quarter or the categorical field is never touched, there's no forecast to audit at all — the number defended in the Monday meeting isn't coming from the CRM, and no CRM fix improves it; (c) if the category field is used but "Commit" systematically slips, that's a judgment and deal-review problem, not a data-quality finding. Treating one for the other is the most common way a RevOps fix ends up "recalibrate the stages" when the real gap was that nobody fills in the manual forecast field.

**A fourth native field sits next to those three, and it is not a forecast input.** `hs_deal_score` — HubSpot's own field description: "the predictive deal score calculated by HubSpot AI to score the deal health" — is a number field with no documented scale or bounds, distinct from `hs_deal_stage_probability` and from the manual forecast trio above. Read literally, it scores the deal's health, not its odds of closing, so don't fold it into a forecast-accuracy variance calculation and don't average or sum it with `hs_deal_stage_probability`. It depends on Sales Hub Professional or above — check whether it's even populated on this portal before citing it. Don't assume the populated values spread evenly across 0–100 either: sort the portal's own deals by this field before calling any single score "high" or "low" — a portal's real distribution can sit entirely in a low-to-mid band, where a score that looks mediocre against an assumed full scale is actually the ceiling anyone on that portal has ever seen. Treat it as a cross-check a rep or manager can glance at before a deal-review conversation, not as a fourth forecast signal to reconcile against the other three.

**Pipeline coverage specifically has moved.** The 3–4x multiplier that used to be the standard reference is now cited across 2026 sales-ops sources as too thin — convergence points to 4–6x as the more common target, calculated as 1 / win rate rather than a flat number lifted from a slide: a team closing 20% of its pipeline needs roughly 5x coverage to hit quota, a team closing 33% needs roughly 3x. Same caveat as the rest of this table — vendor convergence, not an analyst-grade source — but a fixed multiplier without checking your own win rate is the more common mistake. That win rate itself should not be blended across the whole book if deal sizes vary widely — a portal running one pipeline for both a $10k SMB motion and a $150k enterprise motion will see very different real conversion rates on each; compute the win rate (and therefore the coverage target) per segment, the same way a stage-to-stage read should never be pooled across pipelines.

**A coverage ratio that looks healthy can still hide two different problems, and the ratio alone won't tell you which.** Sandbagging — a rep quietly pushing a close date out to protect the current period's number, which reappears in next period's coverage — inflates the number without any real change in what's likely to close. Junk pipeline — opportunities logged with no real budget, timeline, or ICP fit, kept open just to keep the ratio green — does the same from the other direction. Coverage answers "is there enough logged," never "is what's logged real." Two cheap checks catch each: a per-rep close-date push-out rate, and stage-to-stage conversion tracked on the same cohort of deals over time rather than a fresh snapshot each week.

**The targets above are a starting point to recalibrate, not a market norm.** No analyst-grade source (Gartner, Forrester, Benchmarkit) publishes a defensible external benchmark for stage-to-stage conversion rates in B2B — figures found across vendor blogs for a comparable step (e.g. MQL→SQL) diverge by a factor of 3 or more depending on how each source defines the stage. Run this table on the account's own closed-won history for at least one full cycle before treating any of these percentages as a pass/fail line. One argument for the weekly cadence itself is better grounded: a 2025 GTM benchmarks report (Ebsta x Pavilion) found teams doing a weekly pipeline review hit 87% forecast accuracy vs. 52% for irregular reviews — a result about review cadence in general, not proof of these specific thresholds.

**If the CRM is HubSpot, check `dealtype` on the client's actual portal before assuming it's still the two-value default (New Business / Existing Business) — don't build a segmentation on a memorized shape.** On a portal where it hasn't been extended, it's a free way to split this whole dashboard without building a custom property first: a closed-won rate or a conversion-rate drop that looks fine blended can be a new-logo problem hiding behind a healthy renewal/expansion base, or the reverse — segment the table by `dealtype` before concluding the pipeline overall is healthy or broken. But plenty of portals do extend it (a custom "Renewal" or "Upsell" value added to the same property), and since Commerce Hub's native Contracts object shipped as a Professional+ public beta in spring 2026, some accounts now track renewal/expansion revenue there instead of on the deal at all. Read `get_properties(deals, [dealtype])` for real before writing this section: if the portal already has finer values, segment on those directly rather than layering a redundant custom property on top; the flat two-value read above is the fallback for a fresh or unextended portal, not the default to assume.

**If the CRM is HubSpot, pull this from the CRM instead of tallying it by hand** — and scope every query to one pipeline at a time. A portal commonly runs several deal pipelines in parallel (main sales, upsell, outbound, partner…) with unrelated stage sets; summing `dealstage` counts across pipelines mixes stages that don't correspond to each other. `hs_is_closed_won`, `hs_is_closed_lost` and `closedate` (a date range, not a single day) are the fields that give a real closed-won rate; a SQL-style query grouped by `dealstage` within one pipeline gives the stage counts behind each conversion row above. The same discipline applies to the dollar-value rows above (Pipeline coverage, Weighted pipeline): sum `amount_in_home_currency`, not the raw `amount` — HubSpot's own connector guidance recommends the home-currency field for financial aggregation, and a portal running deals in more than one currency will silently blend them together if the raw field is summed instead.
